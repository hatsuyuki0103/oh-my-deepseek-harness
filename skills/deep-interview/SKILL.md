# Deep Interview（深度访谈）

## 目的

深度访谈是一个「意图优先」的苏格拉底式澄清循环，发生在任何规划或实现之前。它通过定向提问把模糊想法变成可执行规格：为什么想要这个改动、范围该到哪为止、什么必须排除在外、哪些决定代理可以自行拍板、哪些必须问用户。

## 何时使用

- 需求宽泛、模糊，或缺少具体验收标准
- 用户说「deep interview」「访谈我」「别假设」「把需求问清楚」等
- 需要一份明确的需求产物，再交接给 ralplan / plan / autopilot / ralph / team 等后续技能
- 棕色地带（已有代码库）改动需要先对齐现有规则与术语再动手

## 何时不用

- 需求已指向具体文件/符号，验收标准明确
- 用户明确要求跳过访谈直接执行
- 只是轻量头脑风暴（改用 plan 技能）
- 已有完整 PRD / 计划，应该直接执行

## 为什么存在

执行质量通常卡在意图不清，而不是实现细节不够。一次性展开往往漏掉「为什么改、范围边界、不可接受的取舍、哪些决定仍需用户确认」。本技能用苏格拉底式追问 + 量化歧义评分，让下游执行从一开始就基于明确、可测试、意图对齐的规格。

## 深度档位

- Quick（--quick）：快速预 PRD；阈值 <= 0.30；最多 5 轮
- Standard（--standard，默认）：完整需求访谈；阈值 <= 0.20；最多 12 轮
- Deep（--deep）：高严格度；阈值 <= 0.15；最多 20 轮

max rounds 是硬上限，不是目标轮数。没有达到目标轮数之前，只要歧义已达标并过闸，就立即结晶，不要为凑轮数继续问。未给档位时用 Standard。

## 执行策略

- **每轮只问一个问题**：调用 ask_user_question 时一次只放一个 question，绝不把多轮访谈合并进一次提问。
- **事实自己查，判断问用户**：代码事实用 grep / glob / read / pwsh / web_search 自查；只有意图、边界、取舍、业务规则这些判断才问用户。
- **意图与边界先于实现细节**：先问为什么、范围、非目标、决策边界，再问约束与验收标准。
- **把每个回答当作待检验的声明**：下一问通常应索取证据或例子、暴露隐藏假设、逼迫边界或取舍、或用具体场景压测边界。宁可在一个线索上多问几轮，也不为覆盖而浅尝辄止。
- **事实/判断分类标签**（写进访谈记录，不作别用）：
  - [from-code][auto-confirmed]：能从配置/源码直接确认的高置信事实，不问用户；
  - [from-code]：推断性、模式性、低置信的代码发现，需向用户确认；
  - [from-research]：外部事实（API 限制、兼容性、官方文档），只陈述不决策；
  - [from-user]：目标、偏好、业务逻辑、范围、非目标、验收标准、取舍——一切带决策含义的都必须走用户。
  - 自动确认只限描述性事实；只要一个发现隐含「该怎么做、选哪个方案、什么出界」，就整条归为 [from-user]。
- **棕色地带预检**：第一问之前先读适用的 AGENTS.md、README、docs/ 下的合同/计划/ADR、已有 .omx/context 快照、.omx/specs、项目术语文件（如 CONTEXT.md）。把仓库既有语言当证据而非权威：用户用词与文档/代码冲突时，点名双方来源，问用户以哪个为准。
- **超大上下文的摘要闸**：初始上下文过大时，第一问必须是「请给我一份提示词安全的核心摘要」；摘要记录前不做歧义评分、不过闸、不交接。摘要必须保留目标、约束、成功标准、非目标、决策边界与原文引用。
- **控制提问预算**：只问杠杆最高的问题；能用工具查到的代码事实绝不问用户；保留最新/最高信号的回答，别让超大原文挤掉当前问题。
- **进度透明**：每轮报告轮次、当前最弱维度、歧义分与闸状态。
- **访谈本身不实现**：本技能只产出规格与交接建议，绝不直接改代码。

## 步骤

### Phase 0：预检上下文摄取

1. 从用户输入提取任务 slug（kebab-case）。
2. 尝试加载最近的相关快照 .omx/context/{slug}-*.md。
3. 初始上下文超大时，第一问只请求提示词安全摘要（见上）。
4. 无快照则创建最小快照 .omx/context/{slug}-{YYYYMMDDTHHMMSSZ}.md，字段：任务陈述、期望结果、陈述方案、意图假设、已知事实、约束、未知项、决策边界、可能的代码触点、已读文档、术语冲突、摘要状态。
5. 棕色地带任务在第一问之前完成文档/规则面检查（见执行策略）。

### Phase 1：初始化

1. 解析参数与档位。
2. 用 grep/glob 判定 greenfield（新功能、无现有目标）或 brownfield（改动现有代码）。
3. 记录访谈状态到 .omx/interviews/{slug}-{timestamp}.md（后续每轮追加）：
   - interview_id、档位、类型、初始想法、当前歧义 1.0、阈值、max_rounds、已用挑战模式、阶段（intent-first）、当前焦点维度、上下文快照路径。
4. 开场宣告：档位、阈值、当前歧义分。

### Phase 2：苏格拉底访谈循环

循环直到：歧义 <= 阈值且通过闸审计；或用户带警告退出；或到达 max_rounds。

- **阶段优先级（先完成前阶段再进入后阶段）**：
  - Stage 1 意图优先：Intent（为什么）、Outcome（终态）、Scope（范围）、Non-goals（非目标）、Decision Boundaries（决策边界）
  - Stage 2 可行性：Constraints（约束）、Success Criteria（成功标准）
  - Stage 3 棕色地带落地：Context Clarity（对现有代码的理解）
- **回答后的施压阶梯**：先要例子/反例 → 探隐藏假设 → 逼边界取舍（明确不做/推迟/拒绝什么）→ 用仓库语言挑战模糊术语 → 造一个具体场景压测边界 → 症状还在就重构成本质/根因。
- **广度台账（Breadth Ledger）**：跨线索记录 范围/约束/产出/验证/棕色地带集成 等独立歧义轨道；这是护栏不是轮换规则——当前线索没压透之前不换。
- **文档/术语台账（Docs/Terminology Ledger）**：记录已检视文档路径、仓库规范术语、用户冲突用词、需人决的文档/代码分歧、可建议但不可自动执行的持久化文档项。
- **维度定义**：Intent（为什么）、Outcome（终态）、Scope（范围）、Constraints（必须成立的限制）、Success Criteria（如何判定完成）、Context（现有代码理解，仅棕色地带）。

评分公式：

    greenfield: ambiguity = 1 - (intent*0.30 + outcome*0.25 + scope*0.20 + constraints*0.15 + success*0.10)
    brownfield: ambiguity = 1 - (intent*0.25 + outcome*0.20 + scope*0.20 + constraints*0.15 + success*0.10 + context*0.10)

每维度给出 0.0-1.0 分 + 理由 + 缺口。

- **过闸条件（缺一不可）**：
  1. Non-goals 明确；
  2. Decision Boundaries 明确；
  3. 至少一次施压回访：对早先某个回答做过证据/假设/取舍跟进；
  4. 实用收尾审计通过：再问一轮会实质改变执行，而非润色措辞或追窄边角。
- 歧义 <= 0.10 时，除非是过闸所需的最后一问，否则立即结晶。
- 低分不等于可以无限钻探；剩余不确定不会改变实现时，就结晶。
- **提问方式（ask_user_question）**：
  - 单选轮：options 互斥、单选（不要 multi_select）；推荐项放第一位并标注 "(Recommended)"；
  - 多选轮（收集一组并存的非目标/约束/验收点）：options + multi_select: true；
  - 若一个选项会立刻引出新问题，先单选问这一层，下一轮再问分支；
  - id 用稳定标识（如 round-3-scope），答案会原样回传；
  - 问题以「Round {n} | 目标维度 | 歧义 {x}%」开头，正文一句问清。
- **每轮收尾**：报告评分表、闸状态（Non-goals / Decision Boundaries）、下一焦点维度；把本轮问答与最新评分追加进 .omx/interviews/{slug}-{timestamp}.md。
- **轮次控制**：首次假设探针与一次持续跟进完成前不提供提前退出；连续 3 轮非用户判断（[from-code]/[from-research]）后，下一实质轮必须索取 [from-user] 判断（除非收尾审计已满足）；第 4 轮起允许带警告提前退出；档位中点给软提示；max_rounds 硬停。

### Phase 3：挑战模式（假设压测）

适用时各用一次（记录已用，防重复）：

- **反方（Contrarian）**（第 2 轮起，或回答建立在未验证假设上）：挑战核心假设；
- **术语专家（Terminologist）**（棕色地带，关键术语模糊/冲突时）：按仓库既有语言钉死规范含义；
- **简化者（Simplifier）**（第 4 轮起，或范围膨胀快于结果清晰度）：探最小可行范围；
- **本体论者（Ontologist）**（第 5 轮起且歧义 > 0.25，或用户一直描述症状）：要本质级重构。

### Phase 4：结晶产物

达标（或带警告退出 / 硬停）后：

1. 写访谈转录 .omx/interviews/{slug}-{timestamp}.md（保留问答全程，供下游复用）。
2. 写可执行规格 .omx/specs/deep-interview-{slug}.md，含：
   - 元数据（档位、轮数、最终歧义、阈值、类型）
   - 上下文快照路径（供 ralplan / team 复用）
   - 超大上下文时的提示词安全摘要 + 原文引用
   - 各维度清晰度表
   - Intent / Desired Outcome / In-Scope / Out-of-Scope（Non-goals）/ Decision Boundaries（代理可自行决定什么）/ Constraints / 可测试验收标准
   - 暴露的假设及结论、施压回访发现（回访了哪个回答、改了什么）
   - 棕色地带证据 vs 推断说明、文档/术语台账、场景压测结论
   - 可选持久化文档建议（明确标注 opt-in、公开安全；不自动写公共文档）
   - 技术上下文发现与完整/精简转录

### Phase 5：执行交接

规格是下游唯一需求真源。按场景推荐（用 skill 工具加载对应技能执行；未安装的技能说明当前环境缺失）：

- 需要架构/测试形态审查 → ralplan（或用 plan --consensus），产物 .omx/plans/prd-*.md + test-spec-*.md；
- 规格已足够、直接规划+执行 → autopilot；
- 长期可追踪目标 → DSH goal 工具（create_goal），目标完成验收后 update_goal 标记 complete；
- 用户明确要求持久单主闭环 → DSH 原生 ralph 工具；
- 大规模多路并行 → team / ultrawork（基于 workflow 工具）；
- 仍不够清晰 → 回到访谈循环继续收敛（refine）。

**残余风险规则**：提前退出 / 硬停 / 超阈值带警告继续时，必须在交接物里写明残余风险，让下游知道继承了部分澄清的简报。

**交接时绝不直接实现**——深访是需求模式。

## 工具使用（DSH 版）

- 代码事实：grep / glob / read；命令验证：pwsh；外部最佳实践/版本兼容：web_search。
- 提问：ask_user_question（每轮一问）。
- 状态：.omx/interviews/{slug}-{timestamp}.md（进行中每轮追加）+ .omx/specs/deep-interview-{slug}.md（最终）。
- 快照：.omx/context/{slug}-{timestamp}.md。
- 交接目标技能：skill 工具按名加载（ralplan / plan / autopilot / team / ultrawork / code-review 等）。
- 长期目标：create_goal / get_goal / update_goal；持久闭环：ralph 工具。

## 升级与停止条件

- 用户说停止/取消/中止 → 落盘状态并停；
- 歧义连续 3 轮停滞（+/- 0.05）→ 强制一次本体论者模式；
- 到达 max_rounds → 带残余风险警告交接；
- 所有维度 >= 0.9 → 允许提前结晶（未到 max_rounds 也可）。

## 最终清单

- [ ] 预检快照存在（.omx/context/{slug}-{timestamp}.md）
- [ ] 超大上下文已记录提示词安全摘要后才评分/交接
- [ ] 每轮展示歧义分
- [ ] 意图优先的阶段顺序未被跳过
- [ ] 阶段内始终瞄准最弱维度
- [ ] 结晶前至少一次显式假设探针
- [ ] 至少一次持续跟进/施压回访加深了早先回答
- [ ] 挑战模式按阈值触发（适用时）
- [ ] 转录写入 .omx/interviews/，规格写入 .omx/specs/
- [ ] 棕色地带问题使用证据支撑的确认式提问
- [ ] 棕色地带预检在读文档后再问用户
- [ ] 模糊/冲突术语按仓库语言压测过

## 恢复

中断后重跑：读取最新 .omx/interviews/{slug}-*.md 从当前轮次、评分与闸状态继续；快照与台账都在文件里，无需额外状态服务。

## 推荐三阶段管线

    deep-interview（清晰度闸）-> ralplan（可行性/架构闸）-> autopilot 或 ralph 工具（执行+验证闸）
