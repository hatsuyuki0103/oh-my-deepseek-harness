# Ultrawork（并行执行引擎）

## 定位

Ultrawork 是高吞吐并行执行引擎，是一个**组件**而非持久/验证模式：它提供并行度、上下文纪律与委派判断，但不拥有持久目标跟踪（→ ultragoal）、协调团队生命周期（→ team）、持久单主闭环（→ ralph）、完整自动流水线（→ autopilot）。

## 何时使用 / 何时不用

使用：多个独立任务可同时跑；用户说 "ulw" / "ultrawork" / 明确要并行；任务受益于并发 + 收尾前的轻量证据；想要直接工具通道 + 后台证据通道而不进 team 或持久目标流程。

不用：需要持久目标/台账/跨故事续跑 → ultragoal；需要协调多 worker 生命周期/共享任务状态 → team；需要完整自动流水线 → autopilot；只有一条串行任务 → 直接执行或单 executor；还在共识规划模式 → 留在 ralplan 直到授权执行。

## 执行策略

- **先接地再动手**：一句话任务意图 + 约束 + 会推翻快速修复的未知项；信心不足先勘察收窄，再编辑。
- **执行前定义 pass/fail 验收标准**：结束时什么必须成立？哪个命令/产物能证明？需要什么人工 QA 检查？
- **按依赖形态分类**：独立任务 → 并行通道；共享文件/强前置 → 本地执行或分阶段。
- **自己做 vs 委派，有意选择**：下一步依赖当前仓库上下文/共享文件/紧迭代 → 本地；切片有界、独立、并行显著提效 → subagent 后台委派。
- **双通道并行**：直接工具通道做即时实现/验证；后台证据通道跑文档/测试/回归映射/有界分析（subagent + run_in_background）。
- 独立调用同时发，绝不串行等独立工作；依赖任务等前置完成后才发。
- 长操作（安装/构建/测试套件，约 30 秒+）后台 job；快命令（git status、读文件）前台。

## 步骤

1. **上下文 + 确定性检查**：意图一句、约束与未知列表；信心低先探索。
2. **验收标准先行**：如上。
3. **依赖形态分类**：独立 vs 共享/前置。
4. **自做 vs 委派**：如上。
5. **开通道**：直接通道 + 后台证据通道。
6. **依赖串行**：等前置再发下游。
7. **轻量证据收尾**：构建/类型检查过（适用时）；受影响测试过；人工 QA 备注记录；无新错误引入。

## 委派规则

- 简单查询/有界证据收集 → 低投入 subagent prompt；
- 标准实现/回归工作 → 中投入（roles/executor.md 前缀）；
- 复杂分析/架构审查/高风险多文件改动 → 高投入（roles/architect.md 前缀，只读审查）；
- 官方文档/版本兼容影响正确性 → web_search 证据通道（并行跑，不替代主通道）。

## 状态（文件约定）

轻量：.omx/state/{scope}/ultrawork-state.json —— 启动 {"mode":"ultrawork","active":true,"started_at":...}，每轮推进更新 reinforcement_count，完成 active:false。**ultrawork 不拥有持久台账、架构师签字、完整验证承诺**——直接跑 ultrawork 时不得声称这些保证。

## 升级

- 需要持久目标/故事检查点/跨步骤续跑 → ultragoal；
- 需要协调团队/共享任务状态/持久多 worker 生命周期 → team；
- 用户显式点名的持久单主闭环 → ralph 工具；
- 反复重试仍失败 → 报告问题，不无限重试；
- 依赖不明/需求冲突/验收目标实质分叉 → 上报用户。
